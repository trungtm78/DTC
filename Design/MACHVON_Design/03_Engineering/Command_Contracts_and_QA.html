Publish/rollback theme: giao dịch nguyên tử

1. Authenticate control-plane audience; check current SystemAdmin role.
2. Resolve authorized target tenant. Check active status and requested operation policy.
3. Hash request and acquire idempotency record scoped actor + tenant + operation + key.
   Existing same hash: return committed original response. Different hash:409.
4. BEGIN; SET LOCAL verified tenant context.
5. Lock tenant_theme_pointer row FOR UPDATE, then tenant_theme_review row FOR UPDATE.
6. Recheck actor/token hash/expiry/consumed/base_version and current role revocation policy.
7. For draft review, lock draft and compare revision/hash. For rollback, source version must belong to same tenant.
8. Validate canonical config, six contrast pairs and each referenced asset is clean and same tenant.
9. Insert immutable next version. Update pointer. Mark review consumed. Clear matching draft only.
10. Insert audit(diff metadata) and outbox ThemePublished in same transaction.
11. Persist idempotent response; COMMIT. No provider/network side effects inside transaction.
12. Worker invalidates tenant/version cache; failed delivery retries; clients keep last valid theme until refresh.

Lock order tenant pointer→review→draft luôn thống nhất. Provisioning khởi tạo version1+pointer cùng transaction. Rollback tạo version mới với source_version/reason. API phiên bản mới nhất là nguồn chân lý; localStorage của prototype không nằm trong kiến trúc production. Token raw chỉ trả một lần, server lưu hash; không ghi log.

Nhận diện, kiểm quyền và cache

TenantAdmin chỉ GET /me/tenant/theme; server resolve tenant từ phiên đã xác thực, bỏ tenant override không hợp lệ. SystemAdmin endpoint có policy riêng; tenant role tự định nghĩa không tạo quyền hệ thống. Published DTO không trả actor/token/draft/asset storage key. URL logo cấp qua asset service đã kiểm quyền; không dùng storage key công khai. Conditional GET theo version/ETag và tenant cache key; revalidate khi đăng nhập/chuyển tenant.

Release contract chung

API compatibility: thêm field optional trước, deprecate có thời hạn; mobile schema_version có min_supported. Error envelope dùng Problem duy nhất; tiền decimal string; timestampsUTC. Command thực hiện recheck permission + version + state trong transaction. Không expose generic PATCH role/status/tenant_id. Input allowlist, output projection, pagination và row cap phải có tests.

Test suite chia theo pipeline

PR: lint/type/unit + schema validation + tenant-policy integration + migration new/upgrade. Merge staging: contract/adapter mocks + web/mobile E2E + test dữ liệu. Release: security negative, load, DR, provider sandbox, UAT signoff. Mỗi failed critical case chặn release. Test fixtures, test_cases và readiness được liên kết từ trang bàn giao.

Chuỗi xử lý một command (Cập nhật 1.4 — CR-CCQ-04)

1. Xác thực OIDC (audience đúng plane); tenant đang hoạt động lấy từ membership, X-Tenant-ID chỉ là đề nghị.
2. Kiểm DTO allowlist (trường thừa → 400 FIELD_NOT_ALLOWED), header Idempotency-Key, If-Match khi sửa bản có version.
3. Tra idempotency_record (tenant, actor, operation_id, key): cùng hash → trả phản hồi đã lưu; khác hash → 409 IDEMPOTENCY_CONFLICT; đang xử lý → 409 IDEMPOTENCY_IN_PROGRESS + Retry-After.
4. BEGIN; SET LOCAL app.tenant_id, app.actor_id, app.request_id (RLS PERMISSIVE tenant_access + RESTRICTIVE tenant_boundary).
5. Khóa hàng theo thứ tự cố định của command (khai báo trong đặc tả phân hệ); lock_timeout 3 s [GIẢ ĐỊNH].
6. Kiểm lại quyền + scope + entitlement hiện tại, version (If-Match) và guard của bảng transition (từ, command, đến, quyền, guard).
7. Kiểm quy tắc nghiệp vụ; quy tắc pháp lý lấy theo phiên bản hiệu lực tại ngày nghiệp vụ (legal_basis, R4); ràng buộc DB là lớp phòng thủ cuối.
8. Ghi aggregate (version + 1), audit_event, outbox_event <module>.<aggregate>.<past_tense>.v<n>, idempotency_record (mã + body phản hồi).
9. COMMIT. Không gọi mạng ngoài trong transaction. Retry chỉ cho 40001/40P01, tối đa 3 lần [GIẢ ĐỊNH].
10. Sau commit: outbox relay giao at-least-once; consumer ghi inbox_record (consumer, event_id) để bỏ bản lặp; lỗi quá ngưỡng → DLQ có owner.

Idempotency và If-Match (Cập nhật 1.4 — CR-CCQ-05)

Key giữ tối thiểu 72 giờ [GIẢ ĐỊNH]; lệnh mobile dùng local_uuid làm key và tra trạng thái UNKNOWN bằng GET /sync/commands/{idempotencyKey}; workflow Temporal dùng key wf:{workflowId}:{activityId}:{attempt-group}. Bản ghi có version trả ETag = version; thiếu If-Match → 400 INVALID_REQUEST, lệch → 409 VERSION_CONFLICT. Idempotency key chỉ chặn gửi lặp của cùng một người/màn hình; trùng ý định nghiệp vụ khác key được chặn bằng ràng buộc DB (mục dưới).

Danh mục mã lỗi dùng chung (Cập nhật 1.4 — CR-CCQ-06)

Problem (RFC 7807): type, title, status, code, correlation_id; detail, errors[{field,code,message}], retryable tùy chọn. Mã riêng của phân hệ khai báo ở mục 7 của đặc tả phân hệ. Bí danh cần đổi (yêu cầu cho chủ đặc tả): REVIEW_STALE → REVIEW_INVALID (đã bỏ, CR-SAS-02); IDEMPOTENCY_BODY_MISMATCH (MOB) → IDEMPOTENCY_CONFLICT; SELF_APPROVAL_FORBIDDEN (CTR, PAY) → SELF_APPROVAL_DENIED; 422 PERIOD_LOCKED (MOB) → 409.

Import tệp idempotent và workflow (Cập nhật 1.4 — CR-CCQ-08)

Kho bạc/TABMIS, Hệ thống TTQG về đầu tư công và muasamcong không có API công khai cho bên thứ ba: tích hợp bằng tệp mẫu + đối soát, adapter ở trạng thái PROPOSED/MISSING, không thiết kế lời gọi API giả định. Import tính SHA-256 tệp + khóa nghiệp vụ từng dòng; nạp lại → 409 IMPORT_FILE_ALREADY_APPLIED, không tạo bản ghi; dòng lỗi vào quarantine; ghi domain qua command. Luồng dài (import, phê duyệt nhiều bước, ký số/cấp số, provisioning) chạy trên Temporal; mỗi bước gọi command với key wf:…, guard của bảng transition có quyền từ chối (R9).
